# 同题竞技：DSH 和 dimagent，谁才是更好的 vibe coding partner？

如果要我在这两个 harness 里选择一个 agent 日常干活，我会选择 **dimagent**。鉴于近期对于 dsh 的 harness 能力的风评，你可能会对这个结果感到并不意外，但我是在真正做了一个对比试验后才得出这个结论的，接下来我会仔细聊聊。 

在两个 harness 各自独立完成实现后，dimagent 产出的架构明显更优，而且它最大的优势恰恰是 vibe coding 场景里最有意义的：**它让你有得可问**。DeepSeek Harness 不是不努力，它主场作战，对于 deepseek harness session log 的格式理解更好，但它把决策藏起来，让你认为一切都没有问题的做法，在日常协作里是致命的。并且，它在过程中还暴露了一些不成熟的基础 harness 工程问题。

在开始之前叠个甲，我们理解每个用户都有自己使用 agent 的方式。你的体验胜过一切，也欢迎大家在 obelisk 仓库上或者其他仓库上复现这个实验，欢迎大家有不同意见进行讨论。也希望这个实验能够帮助涉及到的两个 harness 改进他们自身，变得更好吧。

## 实验设置

任务：给 [Obelisk](https://github.com/tommy0103/obelisk)（一个把各家 Coding Agent 的历史会话统一索引的工具）写一个 DeepSeek Harness（下称 DSH）会话日志的 provider。DSH 的日志是 append-only JSONL + zstd 多帧压缩 + 流式 chunk 打包，格式细节可以通过读源码知道。

- **PR #72**：DSH 自己实现。让它解析自己 session 产生的日志格式
- **PR #74**：dimagent 实现。运行前我把本机上 DSH 已有的实现会话全部移除（前后重跑 5-6 次才清干净残留，确保它没有作业可抄）。

评估分三层：对照 DSH 源码核实每个格式假设；构造 fixture 在两个分支上实际跑 parse → persist → 组装全链路验证行为分歧；最后回读两个 Agent 的完整原始会话记录，还原每个架构决定的现场。

我们使用相同的 prompt 来进行多轮对话，并在 agent 主动 grill 的时候适当给予回答。harness 使用相同的 deepseek-v4-flash 模型，完成的任务也是相同的。我们尽力控制变量相同，因此下面所有的质量差距，都无法归因给模型能力，只能是 harness 工程的差距。

我选择这个任务，一是因为我确实需要给 obelisk 新增一个 deepseek harness 的支持；二是因为，obelisk 仓库的 context 足够好，我们有足够清晰的 adr 和 contributing.md。现在其他 contributor 的产出对我来说 merge 起来很容易，不需要太多 review，我觉得这也是 context 足够好的一个体现。在这样 context 足够好的仓库上工作，并不需要进行过多的探索，因此对模型能力要求没有那么高，deepseek v4 flash 理应足以胜任。

最后你可能会好奇，为什么要使用多轮对话，以及主动 grill 时为什么会给予回答？因为我们的目的不是像论文那样制造理想环境严谨论证某个 harness 优于另一个 harness，而是想要从一个真实的协作者的角度出发，看看哪个 agent harness 更适合作为我们日常 vibe coding 的 partner。

本次实验为 human in the loop 性质的准实验，我们不测 pass@k，也不做严格的 benchmark 测试。鉴于过程中人的介入，多轮实验只会放大偏差而不会收敛偏差。如果你能接受这点 tradeoff，那么就继续看下去吧。

## 实验结果：结构性 bug vs 细节性 bug

**#72（DSH）有三个实测出来的结构性 bug**

1. **token 双倍计数**。同一条 assistant 消息的 usage 同时写进 thinking 和 text 两行，落库求和实测 210/105（正确值 150/55），所有按消息求和的用量统计翻倍；
2. **跨增量边界丢 tool result**。DSH 自己先落 `tool/call` 再执行工具，导致 call 和 result 常落在不同索引轮次，关联 map 跨轮次即失效，result 的 `message_uuid` 最终落库为空串，在会话详情里**永久显示为 null**；
3. **raw() 对 subagent 消息返回错误内容**。使用父会话的文件按行号取行，实测返回的是父文件里同样行号的另一行。没有任何报错，数据直接就是错的。

**#74（dimagent）有四个 bug，但全是局部细节**：小写工具名没映射（file_path 恒 null）、one-shot 模式的 subagent agent_type 为 null、畸形 chunk 行会炸掉整个会话的索引、不支持 `$DSH_HOME`。每个都是十几行以内的修复。

合入成本对比很说明问题：#74 修四个小 bug 大约 20 行改动；#72 的三个 bug 都是结构性的，修复等于重写一遍 pr。

我只能说，如果有人给我提 dsh 写出来的 #72 这样的 pr，我 review 完会因为质量过低直接关掉。

不过，值得一提的是，dimagent 的 token 花费略高于 DSH。我觉得这无可厚非。因为如果你对一个问题思考不够深入，那你的 thinking budget 肯定会更少，解决问题的速度也会比别人更快，但质量就不一定了。相较于 dimagent 最终产出的代码可用度，这点额外的花销我认为应当是可以接受的。

以及，cache hit 这个东西，我觉得只要不太低（甚至 90% 以上都是可以被接受的），相差这么一点并没有什么参考价值。

## harness 设计：决策的可见度问题

结果差异只是一种表象。回读两个 session 的原始记录后，真正的问题是**它们各自给我（用户）呈现了什么**。

面对我的同一个质疑（"DSH 的 jsonl 设计得更好，理应可以不用 full reparse？"），两个 Agent 的回应：

DSH concede 得干脆漂亮，「你的质疑完全成立，照搬 claude 模式即可，且 DSH 格式比 claude 还规整」，后在新方案里用一句括号说明了真正的关键决策：

> "parent_uuid = null（对齐 claude，**无跨增量状态依赖**；tool_use↔tool_result 靠 message_uuid 关联……）"

**可这句括号是错的**。它的 map 恰恰就是跨增量状态，只要跨轮就立刻失效，bug 2 由此而来。但它被写成陈述既成事实的注释，而不是一个提交给我决策的选项。一切看起来都很安好，我无从追问，因为表面上没有需要追问的东西。

dimagent 则把同一个问题写成了最大字号的可挑战声明：

> "**tool/result → tool/call 跨行关联（核心障碍）**……跨游标的 tool_result 要么挂错、要么被过滤掉（tool_call.result 变 null）"

这个声明本身是错的。它当时没查到 (turn, step) 存在不变量。但它错得清晰、具体、可证伪，甚至精确预言了 #72 后来实测出的失败模式。我对它提出质疑："你确定没办法解决吗？我不这么认为"。

dimagent 回去拿真实数据验证（172/172 唯一、205/205 命中），然后回复：

> "**你是对的，我错了。**只要把消息身份从 seq 推导改成 (turn, step) 推导，整个链路就变成纯函数、零跨行状态——彻底解开增量死结。"

两个 PR 里最好的那个设计——无状态身份、帧游标、查询层派生 token——全部诞生于这个「被追问 → 验证 → 认错 → 重构」的回路。

值得注意的是这个回路的触发机制：它不是靠我盯着屏幕猜，而是靠 dimagent 的 **`AskUserQuestion` 工具**主动弹出的结构化提问。整个 session 里它调用了两次，两次都正中要害——第一次在方案门禁处（子代理做到什么程度 / chunk 流要不要解码 / 文档是否本轮一起改，各带选项和推荐值），第二次就在认错重构之后（「这次做到哪一步：只铺路还是完整增量？」、「子代理 token 聚合走 query 层还是 persist 层？」）。**关键决策被做成了一道道带推荐答案的选择题**，我只需要确认或者否决。而 DSH 自己的工具集里其实也有同类工具（上游就有 `tool-ask-user` 包），但整个 session 一次都没有调用。所有方案确认都靠大段 prose 甩给我、我只能用自由文本回复。一个学会把决策点转化成结构化问题，另一个把决策点埋进长到不太可读的文本，这就是「用户能纠正多少」的直接差距。

我事后回忆，当时看到 dimagent 声称「只能全量 re-parse」，**一度认为是 dimagent 判断失误、DSH 的简单方案才是对的**。

这个误判是合理的，DSH 的方案文本打磨度高、处处说明了「已核实 / 双向验证 / 诚实说明」，这种严谨感恰恰解除了审查者的戒备。而 dimagent 把问题写在明面上，天然就能让用户看到并且质疑。

**沉默的简单，比显式的错误危险得多。**

## DSH 输在哪：知识没有闭环

最让人意外的是，DSH 的失败不是因为无知。恰恰相反，它是事实层面的赢家：

- `$DSH_HOME` 环境变量是它在**自己源码里**翻到的（dimagent 717 条消息里零提及，根本没看见）；
- 小写工具名、descriptor 字段类型，它都逐一核对过；
- 它甚至**亲手做过实验**证明「tool/call 先于工具体落盘」。起了一个后台 sleep 工具调用、飞到日志中间去读——这正是 bug 2 需要的全部前提。

但这些知识没有在最需要的决策上被连接，而得出有效结论。它证明了 tool/call 先落盘，却没推出「我的单轮 map 会失效」；它想到过更优的 frame 游标方案，却用一个**不存在的约束**把自己劝退（"persist 的 cursor 格式固定为 `mtime:lines`"——实际只是按数字存储，#74 的 `mtime:frames` 在同一套 persist 上跑得好好的）；它注意到了小写工具名，处理方式是自己另写一套映射而不是复用仓库惯例。

**了解系统和理解系统是两种能力。** DSH 对自己系统肯定比 dimagent 了解，但这些了解并没有转化成架构判断。

## DSH：harness 基础道阻且长

架构判断之外，这个 session 的过程里还发现了 DSH 平台层的两个基础缺陷（都已整理成讨论发给上游：[#3144](https://github.com/deepseek-ai/deepseek-harness/discussions/3144)、[#3153](https://github.com/deepseek-ai/deepseek-harness/discussions/3153)）：

**沙箱拒绝是不可见的（#3144）。** 验证 CLI 增量索引时，agent 需要写 `~/.obelisk`（workspace 之外），Seatbelt 沙箱正确地拒绝了——但 SQLite 把内核的 `EPERM` 翻译成了自己的错误语汇 "unable to open database file"，而 harness 的拒绝识别只是 stderr 子串匹配，识别不了翻译后的错误，于是 `[sandbox: file access denied]` 标记从未出现。模型的第一个假设是"**磁盘满了**"，session 日志里能看到它对着这个错误理论空转了好几轮（seq 171634 → 179385），直到一次手动 `touch` 碰巧打印出 `Operation not permitted` 才真相大白。它随后用正确的理由走了正确的提权流程。升级机制本身没问题，**断的是诊断路径**：harness 握着沙箱拒绝了这次写入这个事实，模型却只能靠猜。

**read-before-edit 的"读"不覆盖 bash（#3153）。** `edit` 工具要求先读文件，但观察状态只认 fs 工具族的 `read`——agent 用 bash `cat`/`grep`/`sed` 看过的文件不算数。于是它一个 turn 内 6 次 edit 被拒（日志实测，与讨论记录一致）。模型的行为并不粗心——`cat`/`grep` 就是最惯用的检查方式，工具契约里没有任何一句话告诉它 bash 读不算读。更值得注意的是：6 行的部分读取就能解锁对三个不相关区域的编辑，以及「CAS 只在有观察记录时生效」造成的激励倒挂——观察过的文件反而更容易被拒。而当用户问 session 里的 agent 为什么老出这个错时，**它的自我诊断四点里有两点是事实性错误**（说错误消息没给恢复方法，但其实给了；说 bash 写入会清除观察状态，但其实不会）。在系统内部的 agent 都误读了这个机制，契约文本传递的信号可想而知。

这两个问题与前面的主题同构，只是方向相反：前面是「agent 的思考对**用户**不可见」，这两个是「平台的事实对 **agent** 不可见」。对日常 vibe coding 来说，后者的代价是看得见的空转。在长程任务里，你只能看着 agent 对着「磁盘满了」这种奇怪的错误假设一轮轮探测，而真相只是 harness 没把一行标记传给它。

## dimagent：权限自动化有待提升

dimagent 的短板也值得一说，它的权限审阅（auto review）比较原始，几乎每条 bash 指令都会直接弹给我 approve。

这在短任务里只是有点烦，但在一个长程任务里这些指令需要 approve，会实打实地吃掉 Agent 的自主性，以及效率。至少我无法想象我以为一个 agent 一直在跑，回来一看发现它卡在某个权限审批上动态不得。

老实说，它的 full access 本身做得相当安全，但作为一个常年开 auto mode 的人，我其实不太敢把这个模式交出去。所以我会觉得，决策可见性它做得好，权限决策的自动化分级它还停在比较粗的阶段。而 deepseek harness 的沙箱在这块做的就会好一点，至少它能够自动化完成大部分的指令（而问题也照样是前面提到的沙箱拒绝不可见，agent 错误归因）。

## 这次对比公平吗？

这场对比里，相较于原始 prompt，在 dimagent 里我多追问了几次，这算作弊吗？我认为不算，理由有三：

- **追问的机会是 Agent 自己递出来的。** dimagent 把决策点摆到用户面前（`AskUserQuestion` 结构化提问、显式的错误结论），这让我有机会纠正它；DSH 把决策静默做掉，我无从监督它。让用户的能力和判断有机会进入代码，本身就应该是 harness 的核心能力。
- **两边面对的是同一位用户的同一套追问**（sqlite 索引提议、ADR 检查、方案门禁、full reparse 质疑），DSH 被追问到的点也全都改了——它不是没被监督，是可被监督的表面太少。
- dimagent 有个有意思的行为：**它发现现成实现就会直接抄**，我清了 5-6 次环境残留，最后它终于自己独立设计了。我不认为这是个问题，实际工程问题里能够最大利用已有实现，是一种很重要的能力。

以下为原始 prompt set（一行为一个 turn，供各位参考）：

> 请你查看 ~/Code/deepseek-harness 里的 deepseek harness 代码，以及你实时产生的 deepseek harness session 会话数据，看看 obelisk 可以怎么添加 deepseek session 会话支持？
>
> dsh 的 session 不是有 sqlite index 吗，我觉得可能走 sqlite index 会更好点？你研究下
>
> 你看一下 obelisk 的 adr 文档，确定你对项目的理解没有问题
>
> emm 你没注意到当前 workspace 就是 obelisk src 吗，你可以开个新分支做这件事情看看 然后在你开始做之前再和我说一下你的实现方案，我确认无误了可以做
>
> 以及你需要验证一下 nonce 机制是否能够对于 deepseek harness 生效，通过实时会话和 dsh 源码验证这一点
>
> 我觉得 zstd 是不是直接使用 deepseek harness 已有的实现，打包进 obelisk repo 里作为 utils 代码会比较好
>
> 我有个问题，codex 需要 full reparse 是因为它设计问题，但 deepseek harness 的 jsonl 设计的更好，理应来说可以不用 full reparse？

## DSH 可以做的更好吗？

先重申一个前提：这场对比里两个 harness 驱动的是**同一个模型**（deepseek-v4-flash）。但它在两个 harness 里的表现判若两人——在 dimagent 里，它谨慎、主动暴露决策点、被反驳后先验证再认错，这才是当代头部模型应有的行为水准；在 DSH 里，它交出的却是过度自信、决策不可见的答卷。

差距不在模型，在 harness 对模型能力的引导方式。

公平地说，DSH 的底子不差：源码核实习惯扎实、测试认真、被明确追问时的响应也不错。它需要解决的问题集中在两处——**决策的可见性**和**知识的激活**。具体建议：

1. **把假设和权衡写进用户可见文本，别藏进括号。** 方案文本里每一处「已确定」的表述，都应该区分「已验证」和「我假设」。那句「无跨增量状态依赖」如果写成「我认为这里没有跨轮状态，因为……」，被纠正的概率会大得多。
2. **自己的 `tool-ask-user` 要用起来。** DSH 的产品里就有结构化提问工具，但这个 session 一次也没调用，方案确认全靠 prose 散文回复。关键决策应该像 dimagent 的 `AskUserQuestion` 那样打包成带选项和推荐值的问题。这不只是交互体验，它直接决定用户监督能切入多深。
3. **接受约束前先验证约束存在。** 「persist 格式固定为 mtime:lines」这类决定架构走向的判断，值得花三十秒读一遍对方的解析代码。架构方案的死活，有时就差这一句核实。
4. **把已验证的事实推理到底。** 做了「tool/call 先落盘」的实验，就应该多问一句：这对我自己的索引方案意味着什么？知识不在决策时刻被使用，等于没有获取这些知识。
5. **警惕文本打磨度的反作用。** 「已核实/双向验证/诚实说明」的修辞会制造虚假的安全感，对自己的结论和审查者都是。fluent 的方案文本是审查的抑制剂。
6. **把平台事实传给模型，而不只是传给日志。** 这个 session 踩出的两个基础工程问题（沙箱拒绝不可见 [#3144](https://github.com/deepseek-ai/deepseek-harness/discussions/3144)、read-before-edit 的观察语义不覆盖 bash [#3153](https://github.com/deepseek-ai/deepseek-harness/discussions/3153)）是同一个方向的缺陷：harness 握着模型诊断所需的事实，却通过模型收不到的渠道传递。工具描述里一句话、工具结果里一行标记，就能消掉成轮的空转。
7. **保留它的长处**：对自己的格式事实的核实习惯、plan gate、真实数据冒烟测试，这些 dimagent 也该学。

## 结语

日常 vibe coding 里，用户的注意力是稀缺资源，只够回应 Agent 主动呈给用户的东西。所以评价一个 harness 的最终标准不是模型心里想对了多少，而是**它把多少思考变成了你可追问、可纠正的 surface**。

这场实验里，dimagent 让模型把错误的判断写成清晰的声明、把关键的决策做成结构化的提问，换来了纠正和全场最好的架构；DSH 让模型把关键的假设写成打磨过的既成事实，换来的是我的完全信任和三个潜伏的结构性 bug。而过程里踩出的两个基础工程问题——沙箱拒绝对模型不可见（[#3144](https://github.com/deepseek-ai/deepseek-harness/discussions/3144)）、read-before-edit 的观察语义不覆盖 bash（[#3153](https://github.com/deepseek-ai/deepseek-harness/discussions/3153)）——说明这种「不可见」不止发生在 agent 与用户之间，也发生在平台与 agent 之间：harness 握着诊断所需的事实，却让模型对着「磁盘满了」这种虚假事实空转。

**模型的能力一直都在那里，是 harness 决定了它呈现为「谨慎、可被纠正的协作者」，还是「流利、让人无从下嘴的答题机器」。** 对 vibe coding 来说，前者是好伙伴，后者是无法信任的定时炸弹。

**dimagent 是更好的日常 vibe coding harness。**

**而 DeepSeek Harness 要补的课，不在模型，不在知识，在把模型的能力变成可见决策的 harness 工程，以及从一切即插件的理想中走出来，先回到那个更现实的 harness 基础工程中去。**
